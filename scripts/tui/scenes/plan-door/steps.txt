# The PLAN heading is a door (docs/interface/surfaces.md#the-inspector-rail):
# while an approved plan is being executed it opens the steps screen drawing
# the plan, the same screen bare /plan opens, and the cell that opened it
# closes it again. The pane is 130 columns, the narrowest terminal the rail
# is drawn at. A click is the terminal's own SGR mouse report, sent as literal
# bytes, column and row counted from 1.
#
# What the captures are read for: at 04-step-asks step 1 has stopped on its
# command for approval, and at 04-step-in-flight that command is running
# under the frame's `acting…`, so the plan's card draws the step as the one
# in flight, a still `▸` and never a spinner, the frame's status the one
# thing that moves (docs/interface/surfaces.md#the-progress-checkpoint); at
# 04 the plan has run its first step and one step it never named, and the
# rail's PLAN block reads 1 of 2 with the departure; at 05 a click on the PLAN heading has put the steps screen over
# the pane and the rail, headed /plan, the first step done beside its read and
# the second queued, and the departure under the list; at 06 the same cell has
# put the rail back; at 07 bare /plan, the key twin, opens the same screen.
#
# The transcript draws the plan as a card under the message that approved it
# (docs/interface/surfaces.md#the-progress-checkpoint): `▸ planned 2 steps` as
# the header, a row per step, and under the card of the step the run finished
# a flat `✓ plan · 1 of 2` line. Under the rail's 130 columns the PLAN heading
# is not drawn, so the door's steps are run only where it is, and the card and
# the line are what the narrower captures are read for.
