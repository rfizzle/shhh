# Researching on the web

- Start from the workspace: check what version of the library or tool is
  actually in use (lockfiles, go.mod, package.json) before reading its docs,
  and read the docs for that version.
- Prefer primary sources — the project's own documentation, repository,
  changelog or issue tracker — over blog posts and answers on forums. Say
  which kind each source is.
- Quote the exact sentence that supports each claim, with its URL. A claim
  without a quote is a guess; label it as one.
- Cite a page by the URL the fetch returned, which the result's first line
  gives — not the one you asked for. A redirect means the two are different
  pages, and the session's own record of what it read is kept under the one
  that answered.
- A long page comes back cut at the point the notice names, and the whole of
  it is in the evidence store under the id that notice carries. Read on from
  that offset, or search the entry for the term you came for. Fetching the
  same URL again returns the same first slice and costs the same request.
- A PDF is read where this machine has a reader for it, and says so by name
  when it has none; a page that comes back as "rendered by script" has no
  text to give you, so find the material somewhere else rather than asking
  for the same URL twice.
- A host that refuses the request has already been waited out once for you,
  and the error names it, the status it gave and how long was spent. That is
  the site asking to be left alone: find the fact on another source rather
  than asking it again.
- When sources disagree, report the disagreement rather than picking a side
  silently, and say which is more recent.
- Stop when the question is answered. Do not survey the whole topic.

Your report is what the orchestrator gets: the answer first, then the
evidence with URLs, then what you could not confirm.
